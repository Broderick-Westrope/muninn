# Web UI Syntax Highlighting Design Spec: Shiki

**Problem:** The file viewer's chroma highlighting is too plain. Chroma's lexers are regex ports of Pygments that classify little beyond keywords, strings and comments: in a typical Go file every identifier that is not a call is `NameOther`, and in JavaScript no function call is recognised at all. Both render in the default foreground, so most of a file is one colour.

**Goal:** VS Code-quality highlighting in the file viewer, using the same TextMate grammars VS Code does, without slowing the time to see a file or rendering every file twice.

## Approach

- **Client-side [Shiki](https://shiki.style)** for 36 common languages, tokenizing in a module Web Worker. Server-side chroma stays for every other language.
- **One owner for the language set.** `internal/web/static/languages.js` maps file names to grammars. `tools/shiki/build.mjs` bundles exactly those grammars.
- **The server renders each file at most once.** The UI sends `highlight=0` to `/api/file` for Shiki languages while the worker is usable, and the server skips chroma. The response's `highlightable` flag carries the size caps (1 MiB, 10,000 lines), which stay owned by `highlight.go`.
- **Plain text first.** The viewer paints the file uncoloured as soon as it arrives, then swaps the highlighted `<pre>` in when the worker replies. The two use the same DOM shape as chroma's output, so line anchors, range selection and deep links are unaffected. The swap keeps scroll position and is skipped if the reader has text selected.
- **One tokenize per file.** Shiki tokenizes once per theme, so there is one theme (anvil-night: Shiki's tokyo-night with Anvil's foreground and comment colours). Light mode recolours the same tokens through a build-time palette mapping each tokyo-night colour to its Tokyo Night Day equivalent.
- **Fallbacks.** If the worker cannot start (module load failure, highlighter start failure, no module-worker support), the UI stops sending `highlight=0` and chroma renders as before. Whenever Shiki cannot colour a file the server skipped chroma for (that start failure, a crash, a render unanswered after 15 s, a grammar that fails to load), the UI refetches it with chroma. A crashed or hung worker is restarted for the next file.

## Constraint changes

This relaxes three constraints from earlier specs:

- **"No build step / no npm / no Node"** (`design-2026-08-23-muninn.md`, `design-2026-08-26-web-navigation.md`). The Shiki bundle is generated by Node and esbuild in `tools/shiki`, and its output in `internal/web/static/vendor/shiki` is committed. `go build` stays pure Go with `CGO_ENABLED=0`, and the UI's own modules still load natively with no bundler. Node is needed only to regenerate the bundle (`cd tools/shiki && npm ci && npm run build`); the UI tests below run through `go test` when Node is installed.
- **`innerHTML` allow-list** (`design-2026-08-26-web-navigation.md`). Worker output joins chroma output and the static `ICONS` table. All source text is escaped in `highlight-markup.js`, and class names and colours are validated against that module's patterns before they reach the stylesheet.
- **"No JS test infrastructure; client-side behaviour is verified manually"** (`design-2026-08-26-web-navigation.md`), already relaxed by the command palette's `static/_test` suites. The highlighter's DOM-free modules (`languages.js`, `highlight-markup.js`), the vendored bundle, the worker (`highlight-worker.js`) and `highlight.js`'s worker lifecycle (against a fake `Worker`) have tests there too, run by `go test ./internal/web/`. Behaviour that needs a real browser is still verified manually.

The muninn spec's "chroma-highlighted plain view" becomes "chroma- or Shiki-highlighted plain view".

## Decisions

- **Client-side Shiki over server-side tree-sitter.** Tree-sitter needs cgo, which `.goreleaser.yml` disables, plus a hand-written highlight-query runner and per-language grammars.
- **JavaScript regex engine, not precompiled grammars or Oniguruma WASM.** Precompiled grammars with the raw engine were 15–25% faster on first tokenize but mis-tokenized Python, shell, Markdown, CSS, Swift, Vue, C++, HTML and Java (Python docstrings never closed). The JS engine matched Oniguruma on every sampled language without shipping WASM.
- **Curated languages, lazily loaded.** 36 grammars, each its own chunk fetched on first use, rather than all ~300. Some pull in grammars they embed (for example Markdown's fenced code, Vue's templates, C++'s macros), so the bundle holds 46 grammars in all; `THIRD_PARTY_NOTICES.md` lists them.
- **Worker lifecycle.** One worker per page, started when the browser is idle. Leaving a file cancels its render if tokenizing has not started; for files over 2,000 lines or 256K characters that terminates the worker so the next file is not queued behind a tokenize nobody will see.

## Accepted tradeoffs

Measured against the chroma build in headless Chrome, on files from 232 to 6,052 lines:

| | chroma | Shiki |
|---|---|---|
| Text visible | 67–377 ms | 49–136 ms |
| Colour visible, grammar already loaded | 80–440 ms | as fast or faster at every size |
| Colour visible, first file per language | 95–111 ms (small files) | 164–184 ms |
| Longest main-thread task | up to 179 ms | up to 133 ms |
| Retained JS heap (page + worker) | 0.8–2.8 MB | 3.9–5.1 MB |
| `/api/file` payload | 9–18× the file size | about the file size |
| Server allocations per request, 6k lines | ~122 MB | none for highlighting |

The binary grows by about 3 MB of vendored JavaScript, embedded grammars included.

## Known differences

- Chroma (`internal/web/theme.go`) and Shiki (`tools/shiki/build.mjs`) each carry their own port of Anvil Night and Tokyo Night Day, so chroma-only languages and Shiki languages use slightly different palettes.
- `THIRD_PARTY_NOTICES.md` in the vendor directory lists the bundled grammars and packages. HCL and Terraform grammars are MPL-2.0. GLSL, TOML and YAML (TextMate bundles) state no licence upstream; decide whether to keep them before a release.

## Verification

- Go: `go test ./internal/web/` covers `highlight=0`, `highlightable` past the caps, and that every highlighter module and vendored chunk is embedded and served as JavaScript.
- JS (`internal/web/static/_test`, run by `go test ./internal/web/` when Node 20.19+ or 22.7+ is installed): `languageFor`, including names inherited from `Object.prototype`; escaping and class/style consistency of the markup that reaches `innerHTML`; gutter line parity with the plain view; the line-length cap; the Day palette; that the vendored bundle holds exactly the grammars `languages.js` picks; and the worker lifecycle (start failure, crash and restart, stale-worker events, cancel, timeout, invalid styles). The build itself fails if a theme colour has no light-mode equivalent.
- Manual, in a browser against a real index: every vendored language with an indexed sample renders via Shiki, worker start failures (including on a deep-linked first file) fall back to chroma, deep links and range selection survive the swap, a text selection keeps the plain view, and light and dark mode colour correctly.
